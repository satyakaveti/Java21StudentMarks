Java 10 — var & Performance

A small but impactful release. var reduces boilerplate in local variable declarations without sacrificing static typing. Also includes performance improvements via App CDS.

var — Local Variable Type Inference JEP 286
Used in this project — throughout all service method bodies: var students = repo.findAll().
1 High Level Overview

var lets the compiler infer the type of a local variable from its initializer. It is not dynamic typing — the type is fixed at compile time, just written once. Rules: only in local variable declarations with an initializer; cannot be used in method parameters, return types, fields, or catch clauses (until Java 14 for catch). Greatly improves readability for long generic types.

2 Examples
Cleaner local variablesSimple
// Before var — type repeated
HashMap<String, List<Mark>> marksBySubject = new HashMap<>();
ArrayList<StudentDTO> dtos = new ArrayList<>();

// With var — inferred, still statically typed
var marksBySubject = new HashMap<String, List<Mark>>();
var dtos = new ArrayList<StudentDTO>();

// var in for-each
for (var student : studentRepository.findAll()) {
    System.out.println(student.getName()); // IDE knows type is Student
}

// var with streams
var result = students.stream()
    .filter(s -> !s.isDeleted())
    .collect(Collectors.toList()); // inferred as List<Student>
var in try-with-resourcesMedium
// var works in try-with-resources
try (var conn = dataSource.getConnection();
     var stmt = conn.prepareStatement("SELECT * FROM students WHERE id = ?")) {
    stmt.setLong(1, studentId);
    var rs = stmt.executeQuery();
    while (rs.next()) {
        var name = rs.getString("name");
        System.out.println(name);
    }
}
var in lambda params (Java 11)Real-time
// Java 11 extended var to lambda parameters — allows annotations
marks.stream()
    .filter((@NotNull var m) -> m.getScore() > 0)  // annotation on lambda param
    .map((var m) -> new MarkDTO(m.getId(), m.getSubject().getName(),
                                 m.getScore(), gradeFor(m.getScore()), "PASS"))
    .collect(Collectors.toList());
3 In This Project
service/impl/StudentServiceImpl.java — var used in every method
public ServiceResult<StudentDTO> createStudent(CreateStudentRequest req) {
    var existing = studentRepository.findByRollNumber(req.rollNumber());
    if (existing.isPresent())
        return ServiceResult.validationError("Roll number already exists");

    var student = new Student();
    student.setName(req.name().strip());
    student.setRollNumber(req.rollNumber().strip().toUpperCase());
    student.setEmail(req.email());

    var saved = studentRepository.save(student);
    var dto   = new StudentDTO(saved.getId(), saved.getName(),
                                saved.getRollNumber(), saved.getEmail());

    eventPublisher.publishEvent(new StudentCreatedEvent(saved));
    return ServiceResult.success(dto);
}
Application Class-Data Sharing (App CDS)
Configured in JVM flags for faster dev restarts. Not in application source code.
1 High Level Overview

Class-Data Sharing (CDS) pre-processes class metadata into a shared archive so multiple JVM instances (or restarts) can memory-map it rather than re-parsing class files each time. App CDS (Java 10) extends this to application classes, not just JDK classes. Spring Boot 3.3 adds first-class CDS support via spring.context.checkpoint. Result: significantly faster startup times.

2 Examples
Generate and use CDS archiveSimple
// Step 1: Generate class list
java -Xshare:off -XX:DumpLoadedClassList=app.lst -jar student.jar

// Step 2: Build the shared archive
java -Xshare:dump -XX:SharedClassListFile=app.lst \
     -XX:SharedArchiveFile=app.jsa -jar student.jar

// Step 3: Run with archive (faster startup)
java -Xshare:on -XX:SharedArchiveFile=app.jsa -jar student.jar
Spring Boot 3.3 CDS integrationMedium
// application.yml — Spring Boot 3.3 CDS
spring:
  context:
    checkpoint: onRefresh  // create CDS checkpoint after context refresh

// pom.xml — Maven plugin support
// mvn spring-boot:process-aot  // generates AOT classes
// mvn spring-boot:build-image  // image with CDS baked in
Garbage Collector Interface & G1 GC Improvements
Not in application source code. GC selection is a JVM flag concern. This project uses Generational ZGC in Java 21.
1 High Level Overview

Java 10 introduced a clean GC interface (JEP 304) making it easier to add new GC implementations. It also improved G1 GC: full GC became parallel (previously single-threaded), reducing worst-case pause times significantly. This was an important stepping stone toward ZGC and Shenandoah GC in later versions.

2 Examples
GC flags referenceSimple
// Java 10 — G1 is the default GC, full GC now parallel
java -XX:+UseG1GC -Xms512m -Xmx2g -jar student.jar

// Java 11+ — ZGC available
java -XX:+UseZGC -Xms512m -Xmx2g -jar student.jar

// Java 21 — Generational ZGC (used in this project)
java -XX:+UseZGC -XX:+ZGenerational -Xms512m -Xmx2g -jar student.jar
