Virtual Threads — Standard JEP 444
Used in this project — spring.threads.virtual.enabled=true enables virtual threads for all Tomcat request handling and @Async tasks.
1 High Level Overview

Virtual threads graduate from preview to standard in Java 21. They are now production-ready with no --enable-preview flag. The JVM scheduler (ForkJoinPool-based) multiplexes millions of virtual threads onto a small pool of carrier platform threads. Blocking I/O (JDBC, HTTP, file, Redis) parks the virtual thread without blocking the carrier. Spring Boot 3.2+ enables them with a single property.

2 Examples
Create virtual threadsSimple
// Named virtual thread
Thread vt = Thread.ofVirtual().name("db-worker").start(() -> {
    var result = jdbcTemplate.queryForObject("SELECT ...", String.class);
    System.out.println(result);
});

// Virtual thread executor — 1 million concurrent tasks
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 1_000_000)
        .forEach(i -> exec.submit(() -> processStudent(i)));
}
Why virtual threads matterMedium
// Platform threads: Tomcat has 200 by default
// If each request takes 50ms on DB, max throughput = 200/0.05 = 4,000 req/sec
// When 200 threads all wait on DB, new requests queue

// Virtual threads: each request gets its own virtual thread
// 10,000 concurrent requests → 10,000 virtual threads
// Only ~8 carrier threads, all kept busy with non-blocking work
// Max throughput ≈ 10,000/0.05 = 200,000 req/sec

// The code is identical — no callbacks, no reactive, just blocking:
@GetMapping("/results")
public List<MarkDTO> getResults(@AuthenticationPrincipal UserPrincipal p) {
    return markRepository.findByStudentId(p.getStudentId())  // blocks — fine!
        .stream().map(this::toDTO).collect(Collectors.toList());
}

Record Patterns — Standard JEP 440
Used in this project — destructure ServiceResult subtypes directly in switch arms.
1 High Level Overview

Record patterns graduate to standard in Java 21. They allow inline destructuring of records in instanceof checks and switch expressions. Patterns can be nested to any depth. The _ unnamed pattern (JEP 443) ignores unwanted components. Combined with sealed classes, they provide a complete algebraic pattern matching system.

2 Examples
Destructure in instanceofSimple
record Point(int x, int y) {}
record Circle(Point center, int radius) {}

Object shape = new Circle(new Point(0, 0), 5);

// Without record patterns
if (shape instanceof Circle c) {
    int x = c.center().x();  // still need accessor calls
}

// With record patterns — destructure directly
if (shape instanceof Circle(Point(var x, var y), var r)) {
    System.out.println("Circle at (" + x + "," + y + ") r=" + r);
}
Nested patterns in switchReal-time
// Destructure 2 levels deep — ServiceResult → StudentDTO components
return switch (studentService.getStudent(id, principal)) {
    case ServiceResult.Success(StudentDTO(var sid, var name, var roll, _)) ->
        ResponseEntity.ok(Map.of("id", sid, "name", name, "roll", roll));
    case ServiceResult.NotFound(var msg) ->
        ResponseEntity.status(404)
            .body(ProblemDetail.forStatusAndDetail(NOT_FOUND, msg));
    case ServiceResult.Forbidden(var msg) ->
        ResponseEntity.status(403)
            .body(ProblemDetail.forStatusAndDetail(FORBIDDEN, msg));
    case ServiceResult.ValidationError(var msg) ->
        ResponseEntity.badRequest()
            .body(ProblemDetail.forStatusAndDetail(BAD_REQUEST, msg));
    // Compiler verifies all 4 sealed subtypes covered — no default needed
};

Pattern Matching for Switch — Standard JEP 441
Used in this project — controller dispatches ServiceResult with exhaustive switch, no default needed.
1 High Level Overview

Pattern matching in switch allows case labels with type patterns, guarded patterns (when keyword), and null handling. Combined with sealed classes, the compiler verifies exhaustiveness — compile error if a case is missing. This replaces chains of if/instanceof with clean, verified, readable switch expressions.

2 Examples
Type patterns in switchSimple
// Old — if/instanceof chain
String describe(Object obj) {
    if (obj instanceof Integer i) return "int: " + i;
    else if (obj instanceof String s) return "str: " + s;
    else if (obj instanceof List<?> l) return "list size: " + l.size();
    else return "other";
}

// New — switch with type patterns
String describe(Object obj) {
    return switch (obj) {
        case Integer i       -> "int: " + i;
        case String s        -> "str: " + s;
        case List<?> l       -> "list size: " + l.size();
        case null            -> "null";
        default              -> "other";
    };
}
Guarded patterns with whenMedium
String classify(Object obj) {
    return switch (obj) {
        case Integer i when i < 0      -> "negative int";
        case Integer i when i == 0     -> "zero";
        case Integer i                 -> "positive int: " + i;
        case String s when s.isBlank() -> "blank string";
        case String s                  -> "string: " + s;
        case null                      -> "null";
        default                        -> "other: " + obj.getClass().getSimpleName();
    };
}

controller/AdminController.java

                .body(ProblemDetail.forStatusAndDetail(BAD_REQUEST, msg));
        // Sealed: compiler knows these 4 are all possible cases
    };
}
Sequenced Collections — Standard JEP 431
Used in this project — marks.getFirst() / marks.getLast() on sorted mark lists.
1 High Level Overview

Java 21 introduced three new interfaces: SequencedCollection, SequencedSet, and SequencedMap. They add getFirst(), getLast(), addFirst(), addLast(), removeFirst(), removeLast(), and reversed(). Before this, getting first/last required error-prone list.get(0) / list.get(list.size()-1). All List, Deque, LinkedHashSet, and LinkedHashMap implementations now expose this uniform API.

2 Examples
getFirst, getLast, reversedSimple
List<String> names = new ArrayList<>(List.of("Alice", "Bob", "Charlie"));

// Before Java 21 — verbose and error-prone
String first = names.get(0);               // IndexOutOfBoundsException if empty
String last  = names.get(names.size() - 1); // error-prone

// Java 21 — clean
String first = names.getFirst();  // NoSuchElementException if empty (cleaner)
String last  = names.getLast();

// Reversed view — no copy
List<String> reversed = names.reversed();  // [Charlie, Bob, Alice]

// Works on Deque, LinkedHashSet, LinkedHashMap too
LinkedHashSet<String> set = new LinkedHashSet<>(Set.of("a","b","c"));
set.getFirst();  // first inserted element

    );
}
Unnamed Patterns & Variables JEP 443 — Preview
Used in this project — case NotFound(_) when message not needed, _ in record destructuring to skip fields.
1 High Level Overview

The underscore _ can be used as an unnamed pattern (match a type, don't bind it) or unnamed variable (declare a variable, never use it). In switch: case NotFound(_) matches but ignores the message. In record destructuring: StudentDTO(var id, _, _, _) extracts only id. In catch blocks: catch (IOException _). Eliminates dummy variable names like ignored or unused.

2 Examples
Unnamed in switch and catchSimple
// Unnamed pattern in switch — match type, ignore value
return switch (result) {
    case ServiceResult.Success(var dto)   -> ResponseEntity.ok(dto);
    case ServiceResult.NotFound(_)        -> ResponseEntity.notFound().build();
    case ServiceResult.Forbidden(_)       -> ResponseEntity.status(403).build();
    case ServiceResult.ValidationError(_) -> ResponseEntity.badRequest().build();
};

// Unnamed in catch — exception object not needed
try {
    return processResult(id);
} catch (RuntimeException _) {
    return ResponseEntity.internalServerError().build();
}

// Unnamed variable in try-with-resources
try (var _ = lockService.acquire(studentId)) {
    return markRepository.save(mark);
}
Unnamed in record destructuringMedium
// Only extract id and name from StudentDTO — ignore rollNumber and email
return switch (studentService.getStudent(id, principal)) {
    case ServiceResult.Success(StudentDTO(var sid, var name, _, _)) ->
        "Student #%d: %s".formatted(sid, name);
    case ServiceResult.NotFound(_) ->
        "Not found";
    default ->
        "Error";
};

Scoped Values — Preview JEP 446
Used in this project — pass UserPrincipal request context without ThreadLocal or SecurityContext.
1 High Level Overview

Scoped values enter preview in Java 21 (promoted from incubator in Java 20). They are the modern replacement for ThreadLocal in virtual thread environments. Key advantages over ThreadLocal: immutable (no set()), automatically cleaned up at scope end (no remove()), don't inherit into child virtual threads by default (avoids accidental data sharing), and have lower memory footprint.

3 In This Project
security/JwtAuthFilter.java · aspect/AuditAspect.java
// UserContext.java
public class UserContext {
    public static final ScopedValue<UserPrincipal> CURRENT_USER =
        ScopedValue.newInstance();
}

// JwtAuthFilter — bind user for duration of this request's virtual thread
ScopedValue.where(UserContext.CURRENT_USER, principal)
    .run(() -> filterChain.doFilter(request, response));
// Automatically unbound when run() returns

// AuditAspect — no parameter needed
@Around("@annotation(Auditable)")
public Object audit(ProceedingJoinPoint pjp) throws Throwable {
    var user = UserContext.CURRENT_USER.get();  // always available in request scope
    var start = Instant.now();
    var result = pjp.proceed();
    auditRepo.save(new AuditLog(
        pjp.getSignature().getName(), user.getUsername(),
        Duration.between(start, Instant.now()).toMillis()
    ));
    return result;
}
String Templates — Preview JEP 430
Used in this project — email body construction, log messages, SQL snippet building.
1 High Level Overview

String templates (preview in Java 21, withdrawn in Java 23 for redesign) provide a safe, flexible string interpolation: STR."Hello \{name}". Unlike String.format() or formatted(), templates are processed by a template processor (STR, FMT, or custom) which can validate, escape, or transform the result. STR is the standard interpolating processor. FMT supports format specifiers like \{value:%.2f}.

2 Examples
STR template processorSimple
String name  = "Alice";
int    score = 87;
String grade = "B";

// String.format — positional, error-prone
String msg1 = String.format("Student %s scored %d (%s)", name, score, grade);

// String template — readable, checked at compile time
String msg2 = STR."Student \{name} scored \{score} (\{grade})";

// Multi-line template
String email = STR."""
    Dear \{name},
    Your score for MATHS is \{score}/100.
    Grade: \{grade}
    """;
Custom template processor (SQL safety)Medium
// Custom processor for safe SQL (parameterized)
StringTemplate.Processor<PreparedStatement, SQLException> DB =
    stringTemplate -> {
        String sql = String.join("?", stringTemplate.fragments());
        PreparedStatement stmt = conn.prepareStatement(sql);
        List<Object> params = stringTemplate.values();
        for (int i = 0; i < params.size(); i++)
            stmt.setObject(i + 1, params.get(i));
        return stmt;
    };

// Usage — values auto-parameterized, no SQL injection possible
PreparedStatement ps = DB."SELECT * FROM marks WHERE student_id = \{studentId}
                            AND score >= \{minScore}";

Generational ZGC — Standard JEP 439
Used in this project — JVM flags -XX:+UseZGC -XX:+ZGenerational in production config.
1 High Level Overview

Generational ZGC adds young/old generation collection to ZGC. Most objects are short-lived (DTOs, request objects) — collecting them separately is far more efficient than collecting the whole heap. ZGC always maintained sub-millisecond pauses; Generational ZGC significantly improves throughput by spending less GC effort on long-lived objects. Enabled with -XX:+UseZGC -XX:+ZGenerational. Non-generational ZGC is deprecated in Java 21.

2 Examples
GC comparisonSimple
// G1GC (default) — good throughput, pauses up to 200ms
java -XX:+UseG1GC -jar student.jar

// ZGC (Java 15+) — sub-ms pauses, higher memory overhead
java -XX:+UseZGC -jar student.jar

// Generational ZGC (Java 21) — sub-ms pauses + better throughput
java -XX:+UseZGC -XX:+ZGenerational -jar student.jar

// Impact for Student Portal:
// - StudentDTO, MarkDTO objects → young gen, collected fast
// - Cached entities, connection pools → old gen, rarely collected
// - HTTP request/response objects → young gen, cheap to collect
