Spring Actuator & Micrometer

Actuator exposes operational endpoints — health, metrics, environment, loggers. Micrometer records custom business metrics — marks created per minute, result fetch latency. Together they give full observability into the running Student Portal.

Actuator Endpoints
health, info, metrics, prometheus, loggers, env are exposed. Health is public (for load balancer). All others require ADMIN role.
1 High Level Overview

Add spring-boot-starter-actuator and endpoints appear at /actuator/*. By default most are disabled for security. Expose selectively. Key endpoints: /actuator/health (liveness/readiness), /actuator/metrics (list all metrics), /actuator/metrics/{name} (drill into one), /actuator/loggers (change log level at runtime), /actuator/env (all config properties).

Custom Health Indicator
ResultServiceHealthIndicator checks that the results service can actually query the DB — more meaningful than just "is the JVM alive".
1 High Level Overview

Extend AbstractHealthIndicator and override doHealthCheck(). Call builder.up() or builder.down(). Add details with builder.withDetail(key, value). Your indicator appears under /actuator/health alongside built-in ones (DB, Redis, disk). Kubernetes uses /actuator/health/liveness and /actuator/health/readiness probes.

3 In This Project
metrics/ResultServiceHealthIndicator.java
@Component
public class ResultServiceHealthIndicator extends AbstractHealthIndicator {

    private final MarkRepository markRepository;

    public ResultServiceHealthIndicator(MarkRepository markRepository) {
        this.markRepository = markRepository;
        // Custom message when unhealthy
        super("Result service health check failed");
    }

    @Override
    protected void doHealthCheck(Health.Builder builder) {
        try {
            long markCount = markRepository.count();
            builder.up()
                .withDetail("totalMarks", markCount)
                .withDetail("status", "Result service is operational");
        } catch (Exception ex) {
            builder.down()
                .withDetail("error", ex.getMessage())
                .withDetail("status", "Cannot reach marks table");
        }
    }
}

MeterRegistry
MeterRegistry is Spring's Micrometer entry point — injected into ResultMetrics to register and update custom counters and timers.
1 High Level Overview

MeterRegistry is the central Micrometer interface. Inject it anywhere to create meters. Spring Boot auto-configures it with a backend (Prometheus, Datadog, CloudWatch, etc.) based on what's on the classpath. This project uses Prometheus — the registry automatically formats metrics in Prometheus text format at /actuator/prometheus.

3 In This Project
metrics/ResultMetrics.java
@Component
public class ResultMetrics {

    private final Counter marksCreatedCounter;
    private final Counter marksDeletedCounter;
    private final Timer   resultFetchTimer;

    // MeterRegistry is auto-configured by Spring Boot — just inject it
    public ResultMetrics(MeterRegistry registry) {
        this.marksCreatedCounter = Counter.builder("student.marks.created")
            .description("Total number of marks created")
            .tag("app", "student-portal")
            .register(registry);

        this.marksDeletedCounter = Counter.builder("student.marks.deleted")
            .description("Total number of marks deleted")
            .register(registry);

        this.resultFetchTimer = Timer.builder("student.results.fetch.duration")
            .description("Time taken to fetch student results")
            .publishPercentiles(0.5, 0.95, 0.99)  // p50, p95, p99
            .register(registry);
    }

    public void recordMarkCreated()  { marksCreatedCounter.increment(); }
    public void recordMarkDeleted()  { marksDeletedCounter.increment(); }
    public Timer getResultFetchTimer() { return resultFetchTimer; }
}
Counter
Counts marks created and deleted — lets you graph "marks entered per minute" over time in Grafana to spot activity spikes.
1 High Level Overview

A Counter is a monotonically increasing value. Use it to count events: requests, errors, items processed. Supports tags (labels) for multi-dimensional filtering. Query rate-of-change in Prometheus: rate(student_marks_created_total[5m]) gives marks created per second over 5 minutes.

3 In This Project
service/ResultService.java — counter usage
@Service
public class ResultService {

    private final MarkRepository markRepository;
    private final ResultMetrics metrics;

    public ResultService(MarkRepository markRepository, ResultMetrics metrics) {
        this.markRepository = markRepository;
        this.metrics = metrics;
    }

    @Transactional
    public MarkDTO createMark(Long studentId, CreateMarkRequest request) {
        var mark = new Mark(studentId, request.subjectId(), request.score());
        var saved = markRepository.save(mark);
        metrics.recordMarkCreated();   // increment counter
        return toDTO(saved);
    }

    @Transactional
    public void deleteMark(Long markId) {
        markRepository.deleteById(markId);
        metrics.recordMarkDeleted();   // increment counter
    }
}

// Prometheus query to alert if marks deleted > 10 in 1 minute:
// rate(student_marks_deleted_total[1m]) > 10
Timer
Times result fetch latency — records p50, p95, p99 so you can see "95% of result lookups complete in under 50ms" in Grafana.
1 High Level Overview

A Timer records execution duration and counts invocations. Use timer.record(Runnable) or timer.recordCallable(Callable) to time a block. Timer.Sample is the manual start/stop approach. Timers automatically expose _count, _sum, and _max to Prometheus. Add percentile histograms with publishPercentiles().

public List<MarkDTO> getResults(Long studentId) {
    // Option A: record() wraps the block and handles exceptions
    return metrics.getResultFetchTimer().record(() ->
        markRepository.findByStudentId(studentId)
            .stream().map(this::toDTO).toList()

}

// Option B: manual start/stop (useful when you need the sample object)
public ResultSummaryDTO getSummary(Long studentId) {
    var sample = Timer.start(meterRegistry);
    try {
        return buildSummary(studentId);
    } finally {
        sample.stop(metrics.getResultFetchTimer());
    }
}

@Timed
@Timed on controller methods automatically records HTTP request duration per endpoint — no manual Timer code inside each method needed.
1 High Level Overview

@Timed (Micrometer annotation) automatically creates and records a timer for the annotated method. On controllers, it captures HTTP request duration. On services, it wraps method execution. Requires a TimedAspect bean for non-controller usage.

3 In This Project
controller/ResultController.java · config/MetricsConfig.java
// Controller — @Timed at class level applies to all methods
@RestController
@RequestMapping("/api/results")
@Timed(value = "student.results.api", description = "Result API response times")
public class ResultController {
    // Each method gets: student_results_api_seconds{method="getResults",...}
}

// For @Timed on service methods, register TimedAspect bean
@Configuration
public class MetricsConfig {
    @Bean
    public TimedAspect timedAspect(MeterRegistry registry) {
        return new TimedAspect(registry);
    }
}

// Then on service methods:
@Timed(value = "student.service.createMark", description = "Mark creation time")
public MarkDTO createMark(Long studentId, CreateMarkRequest request) { ... }
@Observed
@Observed on service methods creates automatic tracing spans — visible in distributed tracing tools (Zipkin, Jaeger) as well as metrics.
1 High Level Overview

@Observed (Spring Boot 3.x Micrometer Observation API) is more powerful than @Timed — it records both metrics AND distributed tracing spans in one annotation. Requires ObservedAspect bean and a tracing backend (e.g. Micrometer Tracing with Brave or OpenTelemetry).

3 In This Project
service/ResultService.java · config/ObservabilityConfig.java
// Register ObservedAspect bean
@Configuration
public class ObservabilityConfig {
    @Bean
    public ObservedAspect observedAspect(ObservationRegistry registry) {
        return new ObservedAspect(registry);
    }
}

// Annotate service methods
@Service
public class ResultService {

    @Observed(name = "result.service.getResults",
              contextualName = "fetch-student-results",
              lowCardinalityKeyValues = {"layer", "service"})
    public List<MarkDTO> getResults(Long studentId) {
        return markRepository.findByStudentId(studentId)
            .stream().map(this::toDTO).toList();
        // Creates: a metric AND a trace span named "fetch-student-results"
        // Trace ID propagates to child spans (DB query, cache lookup)
    }
}

//  "message":"Fetching results","traceId":"abc123","spanId":"def456",
//  "studentId":42,"layer":"service"}
Prometheus Scrape Endpoint
GET /actuator/prometheus returns all metrics in Prometheus text format. Prometheus scrapes it every 15 seconds; Grafana dashboards visualise it.
1 High Level Overview

Add micrometer-registry-prometheus to the classpath and Spring Boot automatically exposes /actuator/prometheus. Configure Prometheus to scrape it. The endpoint includes JVM metrics (heap, GC, threads), HTTP metrics (requests per endpoint, latency), and your custom counters and timers — all in one response.

Structured Logging
In prod profile, logging.structured.format.console=ecs outputs JSON logs — each log line is a JSON object with timestamp, level, message, traceId, spanId, and all MDC fields.
1 High Level Overview

Spring Boot 3.2 added native structured logging. Set logging.structured.format.console=ecs (Elastic Common Schema) or logstash in application-prod.yml. Log lines become JSON objects that log aggregators (ELK, Datadog, Loki) can parse and query. Trace IDs from Micrometer Tracing appear automatically.
