Spring Cache

Spring's caching abstraction sits between your service and the database. Add @Cacheable to a method and results are stored in Redis for 5 minutes — subsequent calls skip the DB entirely. @CachePut refreshes the cache on update. @CacheEvict removes stale entries on delete.

How Spring Cache Works
Spring wraps @Cacheable methods in a proxy. On call: check cache first → if hit, return cached value; if miss, call real method and store result.
1 High Level Overview

Spring Cache is an abstraction — the same annotations work with any backing store (Redis, Caffeine, EhCache, ConcurrentHashMap). The annotations work via AOP proxies. Key points:

AnnotationWhen it firesWhat it does
@CacheableBefore the methodReturn cached value if present; else call method + cache result
@CachePutAfter the methodAlways calls the method + updates the cache with the result
@CacheEvictBefore or afterRemoves one or all entries from the cache
@Caching—Group multiple cache annotations on one method

⚠️ Self-invocation problem: if ServiceA.methodA() calls this.methodB() where methodB is @Cacheable, the cache is bypassed — Spring's proxy is not involved. Always call through the proxy (inject the service into itself, or use ApplicationContext).

RedisCacheManager with TTL
Configured with 5-minute TTL for "results" cache and 10-minute TTL for "students" cache. JSON serialisation so cached data is human-readable in Redis CLI.
1 High Level Overview

RedisCacheManager connects Spring's cache abstraction to Redis. Key configuration choices: TTL (how long cached entries live), serialisation (how values are stored — use JSON for readability and cross-service sharing), and null value handling (disable to avoid caching null results).

3 In This Project
config/CacheConfig.java
@Configuration
@EnableCaching
public class CacheConfig {

    @Bean
    public CacheManager cacheManager(RedisConnectionFactory factory) {
        // Default config — used for any cache not explicitly configured
        var defaultConfig = RedisCacheConfiguration.defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(5))
            .disableCachingNullValues()
            .serializeKeysWith(RedisSerializationContext.SerializationPair
                .fromSerializer(new StringRedisSerializer()))
            .serializeValuesWith(RedisSerializationContext.SerializationPair
                .fromSerializer(new GenericJackson2JsonRedisSerializer()));

        return RedisCacheManager.builder(factory)
            .cacheDefaults(defaultConfig)
            // Per-cache TTL overrides
            .withCacheConfiguration("results",
                defaultConfig.entryTtl(Duration.ofMinutes(5)))
            .withCacheConfiguration("students",
                defaultConfig.entryTtl(Duration.ofMinutes(10)))
            .withCacheConfiguration("subjects",
                defaultConfig.entryTtl(Duration.ofHours(1)))  // subjects rarely change
            .build();
    }
}
@Cacheable
getResults(studentId) is @Cacheable — first call hits DB and caches result; subsequent calls return from Redis in <1ms until TTL expires.
1 High Level Overview

@Cacheable is the most common annotation. The key expression (SpEL) determines the Redis key. The condition expression can skip caching based on parameters. The unless expression can skip caching based on the result. Default key = all parameters.

2 Examples
Basic @CacheableSimple
// Redis key: "results::42"  (cache name + "::" + key expression)
@Cacheable(value = "results", key = "#studentId")
public List<MarkDTO> getResults(Long studentId) {
    // This DB query only runs on cache miss
    return markRepository.findByStudentId(studentId)
        .stream().map(this::toDTO).toList();
}
Conditional cachingMedium
// Only cache if studentId > 0 (condition = before method)
// Don't cache if result is empty (unless = after method, based on return value)
@Cacheable(value = "results",
           key = "#studentId",
           condition = "#studentId != null",
           unless = "#result.isEmpty()")
public List<MarkDTO> getResults(Long studentId) {
    return markRepository.findByStudentId(studentId)
        .stream().map(this::toDTO).toList();
}

service/ResultService.java
@Service
public class ResultService {

    private final MarkRepository markRepository;

    @Cacheable(value = "results", key = "#studentId")
    public List<MarkDTO> getResults(Long studentId) {
        log.debug("Cache MISS for studentId={} — querying DB", studentId);
        return markRepository.findByStudentId(studentId)
            .stream().map(this::toDTO).toList();
        // Second call with same studentId: log line never prints — served from Redis
    }

    @Cacheable(value = "students", key = "#id")
    public StudentDTO getStudentById(Long id) {
        return studentRepository.findById(id)
            .filter(s -> !s.isDeleted())
            .map(this::toStudentDTO)
            .orElseThrow(() -> new StudentNotFoundException(id));
    }
}
@CachePut
When admin updates a mark, @CachePut updates the Redis entry immediately — so the student sees fresh data without waiting for TTL to expire.
1 High Level Overview

@CachePut always calls the method and always updates the cache. Unlike @Cacheable, it never skips the method. Use it on update methods to keep the cache in sync. The key must match what @Cacheable uses on the read method.

3 In This Project
service/ResultService.java
// key must match @Cacheable key on getResults()
@CachePut(value = "results", key = "#result.studentId()")
public List<MarkDTO> updateMark(Long markId, UpdateMarkRequest request) {
    var mark = markRepository.findById(markId)
        .orElseThrow(() -> new MarkNotFoundException(markId));
    mark.setScore(request.score());
    markRepository.save(mark);

    // Return the full updated list — this becomes the new cached value
    return markRepository.findByStudentId(mark.getStudent().getId())
        .stream().map(this::toDTO).toList();
}
// After this: Redis key "results::<studentId>" holds the fresh list
@CacheEvict
Deleting a mark or student evicts their cache entry. The next read goes to DB and re-populates the cache fresh.
1 High Level Overview

@CacheEvict removes entries from the cache. allEntries = true clears the entire named cache. beforeInvocation = true evicts before the method runs (useful to ensure stale data is never served even if the method fails).

2 Examples
Evict single entrySimple
@CacheEvict(value = "results", key = "#studentId")
public void deleteAllMarksForStudent(Long studentId) {
    markRepository.deleteByStudentId(studentId);
    // Cache entry "results::<studentId>" is removed after this returns
}
Evict all + multiple cachesMedium
// Evict from both caches when a student is deleted
@Caching(evict = {
    @CacheEvict(value = "results",  key = "#id"),
    @CacheEvict(value = "students", key = "#id")
})
public void softDeleteStudent(Long id) {
    var student = studentRepository.findById(id)
        .orElseThrow(() -> new StudentNotFoundException(id));
    student.setDeleted(true);
    studentRepository.save(student);
}
Scheduled Full Cache Flush
Every night at midnight, all cache entries are cleared so the next day starts with fresh data from the DB — prevents long-lived stale data.
3 In This Project
scheduler/CacheRefreshScheduler.java
@Component
public class CacheRefreshScheduler {

    private final CacheManager cacheManager;

    public CacheRefreshScheduler(CacheManager cacheManager) {
        this.cacheManager = cacheManager;
    }

    // Every night at midnight — full cache flush
    @Scheduled(cron = "0 0 0 * * *")
    @CacheEvict(value = {"results", "students", "subjects"}, allEntries = true)
    public void flushAllCaches() {
        log.info("[CACHE] Nightly full flush completed");
    }

    // Every 5 minutes — refresh subjects cache (rarely changes but keep it fresh)
    @Scheduled(fixedRate = 300_000)
    public void refreshSubjectsCache() {
        var cache = cacheManager.getCache("subjects");
        if (cache != null) cache.clear();
    }
}
JSON Serialisation in Redis
GenericJackson2JsonRedisSerializer stores cache values as readable JSON in Redis — you can inspect them with redis-cli and they survive app restarts.
1 High Level Overview

By default, Spring uses Java serialisation for Redis values — produces binary, not readable. GenericJackson2JsonRedisSerializer stores values as JSON with a @class field for type information. This enables cross-service cache sharing and human-readable inspection. Values must be Jackson-serialisable (no cycles, proper getters).
