Spring Core — IoC, Dependency Injection & Bean Lifecycle

The foundation of everything in Spring. The IoC container owns all objects (beans), wires dependencies automatically, and manages the full lifecycle from creation to destruction. Understanding this module is understanding Spring itself.

IoC Container
The entire project runs inside the Spring IoC container — every service, controller, repository, and filter is a bean managed by it.
1 High Level Overview

Inversion of Control means your code no longer controls object creation — Spring does. You describe what you need; the container figures out how to build and wire it. The container is represented by ApplicationContext, which holds all beans, resolves dependencies, applies proxies (AOP, transactions, caching), and fires lifecycle callbacks.

Instead of new StudentService(new StudentRepository(new DataSource(...))), you just declare StudentService needs a StudentRepository and Spring handles the rest. This enables loose coupling, easy testing, and configuration-driven behaviour.

2 Examples
Without IoC vs With IoCSimple
// ❌ Without IoC — tight coupling, impossible to unit test
public class StudentController {
    private StudentService service = new StudentService(
        new StudentRepository(DataSourceFactory.create())
    );
}

// ✅ With IoC — Spring builds and injects everything
@RestController
public class StudentController {
    private final StudentService studentService;
    public StudentController(StudentService studentService) {
        this.studentService = studentService;
    }
}
ApplicationContext directlyMedium
// Spring Boot creates this for you on startup — you rarely need it directly
// But it's good to know what's happening under the hood
@SpringBootApplication
public class StudentPortalApplication {
    public static void main(String[] args) {
        ApplicationContext ctx = SpringApplication.run(StudentPortalApplication.class, args);

        // All beans are now available
        StudentService service = ctx.getBean(StudentService.class);
        String[] allBeans = ctx.getBeanDefinitionNames(); // every registered bean
        System.out.println("Beans loaded: " + allBeans.length);
    }
}
Constructor Injection
Used everywhere in this project — all controllers, services, repositories use constructor injection. No @Autowired on fields.
1 High Level Overview

Spring supports three DI styles: field injection (@Autowired on field), setter injection, and constructor injection. Constructor injection is the best practice because: dependencies are explicit, the class is immutable (final fields), and you can unit-test without Spring by just calling new MyService(mockRepo). Spring Boot auto-detects a single constructor and injects it — no annotation needed.

2 Examples
Field vs Constructor injectionSimple
// ❌ Field injection — hard to test, hidden dependencies
@Service
public class ResultService {
    @Autowired private MarkRepository markRepository;  // can't make final
    @Autowired private StudentRepository studentRepository;
}

// ✅ Constructor injection — explicit, testable, immutable
@Service
public class ResultService {
    private final MarkRepository markRepository;
    private final StudentRepository studentRepository;

    // Spring injects both automatically — no @Autowired needed
    public ResultService(MarkRepository markRepository,
                         StudentRepository studentRepository) {
        this.markRepository = markRepository;
        this.studentRepository = studentRepository;
    }
}

// Unit test — no Spring context needed at all
class ResultServiceTest {
    @Test void testSummary() {
        var service = new ResultService(mockMarkRepo, mockStudentRepo);
        // test directly
    }
}
Multiple constructors — use @Autowired on oneMedium
@Service
public class NotificationService {
    private final EmailClient emailClient;
    private final AppProperties appProperties;
    private final ApplicationEventPublisher publisher;

    // When multiple constructors exist, mark the one Spring should use
    @Autowired
    public NotificationService(EmailClient emailClient,
                                AppProperties appProperties,
                                ApplicationEventPublisher publisher) {
        this.emailClient = emailClient;
        this.appProperties = appProperties;
        this.publisher = publisher;
    }

    // Secondary constructor for testing — Spring ignores this one
    public NotificationService(EmailClient emailClient) {
        this(emailClient, AppProperties.defaults(), null);
    }
}

Bean Stereotypes
Every layer uses a different stereotype — @RestController for web, @Service for business logic, @Repository for DB, @Component for everything else.
1 High Level Overview

All stereotypes are specialisations of @Component — they all register a bean. The difference is semantics and additional behaviour: @Repository enables exception translation (converts JDBC exceptions to Spring's DataAccessException). @Service is a marker for business logic. @RestController = @Controller + @ResponseBody.

StereotypeLayerExtra Behaviour
@ComponentAnyBase — just registers a bean
@ServiceBusiness logicSemantic marker only
@RepositoryData accessException translation
@ControllerWeb MVCRegisters as MVC handler
@RestControllerREST API= @Controller + @ResponseBody
@ConfigurationConfigCGLIB proxy — @Bean methods are intercepted

@Configuration & @Bean
Used in CacheConfig, SecurityConfig, AsyncConfig, JpaConfig — anywhere we need to configure third-party beans or complex wiring.
1 High Level Overview

@Configuration classes are the programmatic alternative to XML. @Bean methods declare beans you need full control over — typically third-party objects you can't annotate. Spring proxies @Configuration classes with CGLIB, so calling one @Bean method from another always returns the same singleton instance.

2 Examples
Simple @Bean registrationSimple
@Configuration
public class AppConfig {

    // Spring calls this once, registers return value as a singleton bean
    @Bean
    public BCryptPasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder(12);
    }

    // Spring injects the bean above automatically into this method
    @Bean
    public AuthenticationManager authManager(AuthenticationConfiguration config)
            throws Exception {
        return config.getAuthenticationManager();
    }
}
Full cache config with TTLMedium
@Configuration
@EnableCaching
public class CacheConfig {

    @Bean
    public RedisCacheConfiguration defaultCacheConfig() {
        return RedisCacheConfiguration.defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(5))
            .disableCachingNullValues()
            .serializeValuesWith(RedisSerializationContext.SerializationPair
                .fromSerializer(new GenericJackson2JsonRedisSerializer()));
    }

    @Bean
    public CacheManager cacheManager(RedisConnectionFactory factory,
                                     RedisCacheConfiguration defaultConfig) {
        return RedisCacheManager.builder(factory)
            .cacheDefaults(defaultConfig)
            .withCacheConfiguration("results",
                defaultConfig.entryTtl(Duration.ofMinutes(5)))
            .withCacheConfiguration("students",
                defaultConfig.entryTtl(Duration.ofMinutes(10)))
            .build();
    }
}
Async config with virtual thread executorReal-time
@Configuration
@EnableAsync
public class AsyncConfig {

    // Java 21 virtual thread executor for all @Async methods
    @Bean(name = "virtualThreadExecutor")
    public Executor virtualThreadExecutor() {
        return Executors.newVirtualThreadPerTaskExecutor();
    }

    // Configure @Async to use this executor by default
    @Bean
    public AsyncConfigurer asyncConfigurer() {
        return new AsyncConfigurer() {
            @Override
            public Executor getAsyncExecutor() {
                return virtualThreadExecutor();
            }
            @Override
            public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
                return (ex, method, params) ->
                    log.error("Async error in {}: {}", method.getName(), ex.getMessage());
            }
        };
    }
}

@Profile
Used for DevDataSeeder (dev only), mock email service (test only), structured logging (prod only).
1 High Level Overview

@Profile activates a bean only when a specific Spring profile is active. Profiles are set via spring.profiles.active in properties, environment variable, or JVM arg. This project uses three profiles: dev (Docker Compose, seed data, verbose SQL), test (Testcontainers, mock email), and prod (connection pool tuning, JSON logs).

2 Examples
Profile-specific beansSimple
@Service @Profile("!prod")   // active in dev and test, NOT in prod
public class MockEmailService implements EmailService {
    public void send(String to, String subject, String body) {
        System.out.println("[MOCK EMAIL] To: " + to + " | " + subject);
    }
}

@Service @Profile("prod")    // active only in prod
public class SmtpEmailService implements EmailService {
    public void send(String to, String subject, String body) {
        // real SMTP send
    }
}

@Conditional
Used to register Redis cache service only when app.cache.enabled=true, with a NoOp fallback when Redis is unavailable.
1 High Level Overview

Spring Boot provides ready-made @Conditional variants: @ConditionalOnProperty, @ConditionalOnMissingBean, @ConditionalOnClass, @ConditionalOnBean. These power all of Spring Boot's auto-configuration — beans are only created when specific conditions are met, making the framework zero-config by default but fully overrideable.

2 Examples
ConditionalOnPropertySimple
@Bean
@ConditionalOnProperty(name = "app.notifications.email.enabled",
                        havingValue = "true",
                        matchIfMissing = false)
public EmailNotificationListener emailListener(NotificationService svc) {
    return new EmailNotificationListener(svc);
}
// Only registers the listener if app.notifications.email.enabled=true in yml
ConditionalOnMissingBean fallbackMedium
@Configuration
public class CacheServiceConfig {

    // Primary: Redis cache — used when Redis is on the classpath and configured
    @Bean
    @ConditionalOnProperty(name = "app.cache.enabled", havingValue = "true", matchIfMissing = true)
    public ResultCacheService redisCacheService(RedisTemplate<String, Object> redis) {
        return new RedisCacheService(redis);
    }

    // Fallback: no-op cache — activates only if no other ResultCacheService was registered
    @Bean
    @ConditionalOnMissingBean(ResultCacheService.class)
    public ResultCacheService noOpCacheService() {
        return new NoOpCacheService();  // passthrough, no caching
    }
}
ApplicationRunner
Used as DevDataSeeder — seeds students and subjects into the DB after the full application context is started in dev mode.
1 High Level Overview

ApplicationRunner (and CommandLineRunner) are called by Spring Boot after the entire context is fully started and ready. Use them for startup tasks: DB seeding, cache warming, config validation. ApplicationRunner receives typed ApplicationArguments; CommandLineRunner receives raw String[]. Multiple runners are ordered with @Order.

2 Examples
Seed subjects on startupSimple
@Component
@Order(1)  // runs before other runners
public class SubjectSeeder implements ApplicationRunner {

    private final SubjectRepository subjectRepository;

    public SubjectSeeder(SubjectRepository subjectRepository) {
        this.subjectRepository = subjectRepository;
    }

    @Override
    public void run(ApplicationArguments args) {
        if (subjectRepository.count() == 0) {
            subjectRepository.saveAll(List.of(
                new Subject("MATHS"),
                new Subject("SCIENCE"),
                new Subject("ENGLISH")
            ));
        }
    }
}
Cache warm-up on startupMedium
@Component
@Order(2)
@Profile("prod")
public class CacheWarmupRunner implements ApplicationRunner {

    private final ResultService resultService;
    private final StudentRepository studentRepository;

    public CacheWarmupRunner(ResultService resultService,
                              StudentRepository studentRepository) {
        this.resultService = resultService;
        this.studentRepository = studentRepository;
    }

    @Override
    public void run(ApplicationArguments args) {
        // Pre-populate cache for top 50 most-active students
        studentRepository.findTopActiveStudents(50)
            .forEach(s -> resultService.getResults(s.getId())); // populates @Cacheable
        System.out.println("[STARTUP] Cache warmed up for 50 students.");
    }
}
BeanPostProcessor
Used to detect all beans implementing Auditable and initialise their audit metadata fields after creation.
1 High Level Overview

BeanPostProcessor intercepts every bean after it is created and lets you modify it. Spring itself uses this extensively — @Transactional, @Async, and @Cacheable all work via BeanPostProcessors that wrap beans in proxies. You implement two methods: postProcessBeforeInitialization (before @PostConstruct) and postProcessAfterInitialization (after).

2 Examples
Detect and initialise Auditable beansReal-time
@Component
public class AuditSetupPostProcessor implements BeanPostProcessor {

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        // Java 16 pattern matching instanceof — no cast needed
        if (bean instanceof Auditable auditable) {
            auditable.initAuditFields();
        }
        return bean;  // MUST return the bean (or a proxy wrapping it)
    }
}

// Any bean implementing this gets initAuditFields() called after creation
public interface Auditable {
    void initAuditFields();
    LocalDateTime getLastModifiedAt();
    default boolean isRecentlyModified() {
        return Duration.between(getLastModifiedAt(), LocalDateTime.now()).toHours() < 24;
    }
}
@Lazy
Used on the virtual thread executor bean and heavy third-party clients — created only when first needed, not at startup.
1 High Level Overview

By default, Spring creates all singleton beans at startup (eager). @Lazy defers creation until the bean is first requested. Useful for: expensive-to-create beans you might not use, breaking circular dependencies, and speeding up startup in dev. Note: lazy beans still participate in normal Spring lifecycle once created.

2 Examples
Lazy executor + lazy HTTP clientSimple
@Configuration
public class AsyncConfig {

    @Bean
    @Lazy  // thread pool not created until first @Async method fires
    public Executor virtualThreadExecutor() {
        return Executors.newVirtualThreadPerTaskExecutor();
    }
}

@Configuration
public class HttpClientConfig {

    @Bean
    @Lazy  // HTTP client not created until first external API call
    public GradeImportClient gradeImportClient() {
        return HttpServiceProxyFactory
            .builderFor(RestClientAdapter.create(
                RestClient.builder()
                    .baseUrl("https://grades.external.com")
                    .build()))
            .build()
            .createClient(GradeImportClient.class);
    }
}
