Spring Data JPA

All database access in this project goes through Spring Data JPA repositories. Hibernate 6 handles SQL generation. Flyway runs the migrations. Every pattern — derived queries, JPQL, native SQL, projections, specifications, auditing, optimistic locking, and soft delete — is used in the Student Portal.

Entities & Mappings
Student, Subject, Mark, User, Role, AuditLog — all are JPA entities mapped to PostgreSQL tables created by Flyway migrations.
1 High Level Overview

A JPA entity is a Java class mapped to a DB table. @Entity registers it, @Table names the table, @Id marks the primary key, @GeneratedValue handles auto-increment. @Column customises column names and constraints. Hibernate 6 (Boot 3.x) generates the SQL from these annotations.

2 Examples
Basic entitySimple
@Entity
@Table(name = "subjects")
public class Subject {

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE,
                    generator = "subject_seq")
    @SequenceGenerator(name = "subject_seq",
                       sequenceName = "subject_seq",
                       allocationSize = 50)   // pre-allocates 50 IDs per round
    private Long id;

    @Column(name = "name", nullable = false, unique = true, length = 50)
    private String name;  // MATHS, SCIENCE, ENGLISH
}

    private LocalDateTime updatedAt;
}
Relationships — @ManyToOne, @OneToMany, FetchType.LAZY
Mark belongs to Student and Subject (@ManyToOne). Student has many Marks (@OneToMany). All relationships use FetchType.LAZY to avoid N+1 queries.
1 High Level Overview

JPA relationships: @ManyToOne (FK on this table), @OneToMany (FK on the other table), @ManyToMany (join table). Always use FetchType.LAZY — EAGER loading causes N+1 queries and loads data you don't need. Use JOIN FETCH in JPQL to eagerly load specific associations when needed.

2 Examples
Lazy relationships — correct patternMedium
@Entity
public class Student {

    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE,
                        generator = "student_seq")
    @SequenceGenerator(name = "student_seq", allocationSize = 50)
    private Long id;

    @Column(nullable = false) private String name;
    @Column(nullable = false, unique = true) private String rollNumber;
    @Column(nullable = false, unique = true) private String email;

    // LAZY — marks only loaded when accessed
    @OneToMany(mappedBy = "student", fetch = FetchType.LAZY, cascade = CascadeType.ALL)
    private List<Mark> marks = new ArrayList<>();

    // Soft delete flag — see @SQLDelete below
    @Column(name = "deleted") private boolean deleted = false;
}

@Entity
public class Mark {
    // LAZY — student not loaded unless accessed
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "student_id")
    private Student student;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "subject_id")
    private Subject subject;
}
JOIN FETCH to avoid N+1Real-time
// ❌ N+1 — loads all marks, then for each mark fires a separate query for student
List<Mark> marks = markRepository.findAll();

Repositories — JpaRepository
StudentRepository, MarkRepository, SubjectRepository all extend JpaRepository — getting save, findById, findAll, delete, count, and paginated findAll for free.
1 High Level Overview

JpaRepository<T, ID> provides complete CRUD + pagination + sorting out of the box. Spring Data generates the implementation at runtime — you just define the interface. The hierarchy: Repository → CrudRepository → PagingAndSortingRepository → JpaRepository.

3 In This Project
repository/StudentRepository.java
@Repository
public interface StudentRepository extends JpaRepository<Student, Long>,
                                           JpaSpecificationExecutor<Student> {

    // Derived query — Spring generates: SELECT * FROM students WHERE roll_number = ?
    Optional<Student> findByRollNumber(String rollNumber);

    // Derived query — email lookup for login
    Optional<Student> findByEmail(String email);

    // Existence check — generates: SELECT COUNT(*) > 0 WHERE roll_number = ?
    boolean existsByRollNumber(String rollNumber);

    // Paginated search — full-text via native query
    @Query(value = "SELECT * FROM students WHERE name ILIKE %:name%",
           nativeQuery = true)
    Page<Student> searchByName(@Param("name") String name, Pageable pageable);
}
Derived Query Methods
findByStudentId, findByStudentIdAndSubjectId, existsByRollNumber — Spring generates the SQL from the method name alone, no @Query needed.
1 High Level Overview

Spring Data reads the method name and generates JPQL automatically. Keywords: findBy, countBy, existsBy, deleteBy. Property navigation with And, Or. Comparisons: LessThan, GreaterThan, Between, Like, In. Sorting: OrderByNameAsc.

@Query — JPQL & Native SQL
Average mark per subject, total marks, student rank, full-text name search — all use @Query because the logic is too complex for derived method names.
1 High Level Overview

When derived names can't express the query, use @Query. JPQL uses entity/field names (portable across DBs). Native SQL uses table/column names (database-specific). Use @Param for named parameters. For updates/deletes, add @Modifying + @Transactional.

3 In This Project
repository/MarkRepository.java
@Repository
public interface MarkRepository extends JpaRepository<Mark, Long> {

    // JPQL — entity names, not table names
    List<Mark> findByStudentId(Long studentId);

    // Aggregate — average per subject
    @Query("SELECT m.subject.name, AVG(m.score) FROM Mark m " +
           "WHERE m.student.id = :studentId GROUP BY m.subject.name")
    List<Object[]> findAveragesByStudentId(@Param("studentId") Long studentId);

    // Calculate student rank by total score
    @Query("SELECT COUNT(DISTINCT m.student.id) + 1 FROM Mark m " +
           "GROUP BY m.student.id " +
           "HAVING SUM(m.score) > " +
               "(SELECT SUM(m2.score) FROM Mark m2 WHERE m2.student.id = :studentId)")
    int findRankForStudent(@Param("studentId") Long studentId);

    // Native SQL — full-text search (PostgreSQL ILIKE)
    @Query(value = "SELECT * FROM marks m JOIN students s ON m.student_id = s.id " +
                   "WHERE s.name ILIKE %:name%",
           nativeQuery = true)
    List<Mark> searchByStudentName(@Param("name") String name);

    // Modifying — bulk update with @Modifying
    @Modifying
    @Transactional
    @Query("UPDATE Mark m SET m.score = :score WHERE m.id = :id")
    int updateScore(@Param("id") Long id, @Param("score") int score);

    // Stream — lazy DB cursor for bulk report generation
    @Query("SELECT m FROM Mark m JOIN FETCH m.student JOIN FETCH m.subject")
    Stream<Mark> streamAll();
}
Interface Projections
ResultSummary projection returns only id, subject name, score, and grade — not the full Mark entity. Reduces data fetched from DB and keeps the API response lean.
1 High Level Overview

Interface projections let you select only the fields you need. Define an interface with getter methods matching entity fields. Spring Data generates a proxy that fetches only those columns. More efficient than loading full entities and mapping them manually. Also works with nested properties via default methods.

3 In This Project
dto/ResultSummary.java (projection interface)
// Projection interface — only these fields are fetched
public interface ResultSummary {
    Long getId();
    String getSubjectName();  // maps to mark.subject.name via SpEL
    int getScore();

    // Computed property in the projection
    default String getGrade() {
        int s = getScore();
        if (s >= 75) return "A";
        if (s >= 50) return "B";
        if (s >= 35) return "C";
        return "F";
    }

    default boolean isPassed() {
        return getScore() >= 35;
    }
}

// Repository method using the projection
@Query("SELECT m.id AS id, s.name AS subjectName, m.score AS score " +
       "FROM Mark m JOIN m.subject s WHERE m.student.id = :studentId")
List<ResultSummary> findResultSummaryByStudentId(@Param("studentId") Long studentId);
JpaSpecificationExecutor — Dynamic Filtering
Admin can filter marks by subject, grade range, and date range — all optional. JpaSpecificationExecutor composes Predicate conditions dynamically at runtime.
1 High Level Overview

JpaSpecificationExecutor<T> enables dynamic query building using the Criteria API wrapped in Specification<T> lambdas. Each Specification adds one condition. Combine with and() / or(). Null-safe: skip specs whose filter param is null.

3 In This Project
repository/MarkRepository.java · service/ResultService.java
// Repository extends JpaSpecificationExecutor
public interface MarkRepository extends JpaRepository<Mark, Long>,
                                         JpaSpecificationExecutor<Mark> { }

// Specification factory — each method returns one condition
public class MarkSpecifications {

    public static Specification<Mark> hasSubject(String subjectName) {
        return (root, query, cb) -> subjectName == null ? null :
            cb.equal(root.get("subject").get("name"), subjectName);
    }

    public static Specification<Mark> scoreAtLeast(Integer minScore) {
        return (root, query, cb) -> minScore == null ? null :
            cb.greaterThanOrEqualTo(root.get("score"), minScore);
    }

    public static Specification<Mark> examAfter(LocalDate fromDate) {
        return (root, query, cb) -> fromDate == null ? null :
            cb.greaterThanOrEqualTo(root.get("examDate"), fromDate);
    }
}

// Service — compose dynamically
public Page<MarkDTO> filterMarks(String subject, Integer minScore,
                                   LocalDate from, Pageable pageable) {
    var spec = Specification.where(hasSubject(subject))
                            .and(scoreAtLeast(minScore))
                            .and(examAfter(from));
    return markRepository.findAll(spec, pageable).map(this::toDTO);
}
JPA Auditing
Every entity automatically gets createdAt, updatedAt, createdBy, lastModifiedBy populated by Spring — no manual code needed in service methods.
1 High Level Overview

Enable with @EnableJpaAuditing. Annotate fields: @CreatedDate, @LastModifiedDate, @CreatedBy, @LastModifiedBy. Add @EntityListeners(AuditingEntityListener.class) to each entity. Supply the current user via AuditorAware<String> bean that reads from SecurityContextHolder.

3 In This Project
domain/Student.java · config/JpaConfig.java
// Entity — auditing fields
@Entity
@EntityListeners(AuditingEntityListener.class)
public class Student {
    // ... other fields ...

    @CreatedDate
    @Column(name = "created_at", updatable = false, nullable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    @Column(name = "updated_at", nullable = false)
    private LocalDateTime updatedAt;

    @CreatedBy
    @Column(name = "created_by", updatable = false)
    private String createdBy;   // username from JWT

    @LastModifiedBy
    @Column(name = "last_modified_by")
    private String lastModifiedBy;
}

// Config — tell Spring how to get the current user
@Configuration
@EnableJpaAuditing(auditorAwareRef = "auditorProvider")
public class JpaConfig {

    @Bean
    public AuditorAware<String> auditorProvider() {
        return () -> Optional.ofNullable(SecurityContextHolder.getContext())
            .map(SecurityContext::getAuthentication)
            .filter(a -> a != null && a.isAuthenticated()
                      && !"anonymousUser".equals(a.getPrincipal()))
            .map(Authentication::getName);
    }
}
Optimistic Locking — @Version
Mark entity has @Version — if two admins update the same mark concurrently, the second write throws OptimisticLockException (409 Conflict), preventing silent data loss.
1 High Level Overview

Optimistic locking assumes conflicts are rare. Instead of locking the DB row (pessimistic), it adds a version column. Every update checks WHERE id = ? AND version = ?. If another transaction already updated it (version changed), Hibernate throws ObjectOptimisticLockingFailureException → you catch it and return 409.

3 In This Project
domain/Mark.java · exception/GlobalExceptionHandler.java
// Entity — add @Version field
@Entity
public class Mark {
    @Version
    private Long version;  // Hibernate manages this automatically
    // ...
}

// Hibernate generates:
// UPDATE marks SET score = ?, version = 2 WHERE id = 1 AND version = 1
// If version mismatch → throws OptimisticLockingFailureException

// Exception handler — return 409
@ExceptionHandler(ObjectOptimisticLockingFailureException.class)
public ProblemDetail handleConflict(ObjectOptimisticLockingFailureException ex) {
    var p = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT,
        "This record was updated by another user. Please refresh and try again.");
    p.setTitle("Conflict");
    return p;
}
Soft Delete — @SQLDelete & @Filter
Deleting a student sets deleted=true in the DB — the row is never physically removed. @Filter ensures all queries automatically exclude soft-deleted students.
1 High Level Overview

@SQLDelete overrides Hibernate's DELETE SQL with an UPDATE that sets a deleted flag. @FilterDef + @Filter add a WHERE clause to all SELECT queries for this entity. The filter must be enabled per session — do this in a FilterInterceptor or a BeanPostProcessor.

3 In This Project
domain/Student.java
@Entity
@Table(name = "students")
@SQLDelete(sql = "UPDATE students SET deleted = true WHERE id = ? AND version = ?")
@FilterDef(name = "deletedFilter",
           parameters = @ParamDef(name = "isDeleted", type = Boolean.class))
@Filter(name = "deletedFilter", condition = "deleted = :isDeleted")
public class Student {

    @Column(name = "deleted", nullable = false)
    private boolean deleted = false;

    @Version
    private Long version;
    // ...
}

// Enable the filter for all queries in a request — via interceptor or config
@Component
public class SoftDeleteFilterInterceptor implements HandlerInterceptor {

    @PersistenceContext
    private EntityManager entityManager;

    @Override
    public boolean preHandle(HttpServletRequest req,
                              HttpServletResponse res, Object handler) {
        entityManager.unwrap(Session.class)
            .enableFilter("deletedFilter")
            .setParameter("isDeleted", false);   // always exclude deleted students
        return true;
    }
}
Stream<T> — Bulk Report Generation
streamAll() uses a DB cursor — fetches marks row by row without loading the entire table into memory. Used for generating year-end bulk reports.
1 High Level Overview

Spring Data repository methods can return Stream<T>. Hibernate opens a DB cursor and returns rows lazily — memory stays constant even for millions of rows. Must be used inside a @Transactional method and the stream must be closed (use try-with-resources).

3 In This Project
repository/MarkRepository.java · service/ReportService.java
// Repository — DB cursor
@Query("SELECT m FROM Mark m JOIN FETCH m.student JOIN FETCH m.subject")
Stream<Mark> streamAll();

// Service — process without loading all into memory
@Transactional(readOnly = true)
public void generateYearEndReport(int year, ReportWriter writer) {
    try (var markStream = markRepository.streamAll()) {
        markStream
            .filter(m -> m.getExamDate().getYear() == year)
            .map(m -> new ReportRow(
                m.getStudent().getName(),
                m.getSubject().getName(),
                m.getScore(),
                gradeFor(m.getScore())))
            .forEach(writer::appendRow);
    }
    writer.flush();
}
