Spring Validation

Every request body in this project is validated before it reaches the service layer. Bean Validation annotations on Java records, a custom @MarkRange constraint for 0–100 scores, a DB-backed @UniqueRollNumber constraint, and validation groups for different create vs update rules.

Built-in Constraints
@NotBlank on name and rollNumber, @Size on name, @Min/@Max on scores, @Email on email — all standard Jakarta Validation annotations.
1 High Level Overview

Jakarta Validation (formerly javax.validation) provides a standard set of constraint annotations. Spring Boot 3.x includes the Hibernate Validator implementation. Annotate fields on your request DTOs — Spring checks them before the controller method runs when you add @Valid to the parameter.

@Valid on @RequestBody
Every POST and PUT controller method has @Valid on the @RequestBody parameter — triggers Bean Validation before the method body executes.
1 High Level Overview

Add @Valid (or @Validated) before @RequestBody to trigger validation. If any constraint fails, Spring throws MethodArgumentNotValidException before your method runs. The GlobalExceptionHandler catches this and returns a 400 with field error details. No try/catch in your controller needed.

@Validated on Controllers
@Validated on the controller class enables method-level validation — validates @PathVariable and @RequestParam constraints, not just @RequestBody.
1 High Level Overview

@Validated (Spring's version) on the class enables AOP-based method validation, allowing constraints on @PathVariable, @RequestParam, and method return values. @Valid (Jakarta's version) only works on @RequestBody. For controller parameters other than body, you need @Validated on the class.

2 Examples
Validate path variables and query paramsMedium
@RestController
@RequestMapping("/api/admin")
@Validated   // ← enables method-level validation (not just @RequestBody)
public class AdminController {

    // @Positive validated because @Validated is on the class
    @GetMapping("/students/{id}")
    public StudentDTO getStudent(
            @PathVariable @Positive(message = "ID must be positive") Long id) {
        return studentService.getStudentById(id);
    }

    @GetMapping("/students")
    public Page<StudentDTO> list(
            @RequestParam(defaultValue = "0") @Min(0) int page,
            @RequestParam(defaultValue = "20") @Min(1) @Max(100) int size) {
        return studentService.getAllStudents(PageRequest.of(page, size));
    }
}
Custom @MarkRange Constraint
Scores must be 0–100. Rather than @Min(0) @Max(100) on every field, a single @MarkRange annotation encapsulates the rule and gives a clear, domain-specific error message.
1 High Level Overview

A custom constraint needs two things: an @interface annotation (with @Constraint(validatedBy=)) and a ConstraintValidator<A, T> implementation. The annotation goes on the field; the validator contains the logic. Register by reference — Spring wires the validator as a bean so it can inject repositories.

3 In This Project
validation/MarkRange.java · validation/MarkRangeValidator.java
// 1. Define the annotation
@Target({ElementType.FIELD, ElementType.PARAMETER})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = MarkRangeValidator.class)
@Documented
public @interface MarkRange {
    String message() default "Score must be between 0 and 100";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

// 2. Implement the validator
@Component   // Spring bean — can inject repositories if needed
public class MarkRangeValidator implements ConstraintValidator<MarkRange, Integer> {

    @Override
    public boolean isValid(Integer value, ConstraintValidatorContext context) {
        if (value == null) return false;  // @NotNull handles null separately

        if (value < 0 || value > 100) {
            context.disableDefaultConstraintViolation();
            context.buildConstraintViolationWithTemplate(
                "Score %d is invalid — must be between 0 and 100".formatted(value))
                .addConstraintViolation();
            return false;
        }
        return true;
    }
}

// 3. Use on request records
public record CreateMarkRequest(
    @NotNull Long subjectId,

    @NotNull
    @MarkRange   // ← custom annotation
    Integer score,

    LocalDate examDate
) {}
Custom @UniqueRollNumber — DB Uniqueness Check
Roll numbers must be unique in the DB. @UniqueRollNumber injects StudentRepository and checks before the record is saved — gives a clear validation error instead of a DB constraint violation.
1 High Level Overview

Because the validator is a Spring bean (@Component), it can inject repositories and do DB lookups. This allows uniqueness checks at the validation layer — the caller gets a clean 400 with field-level error instead of a 500 from a DB constraint violation.

3 In This Project
validation/UniqueRollNumber.java · UniqueRollNumberValidator.java
// Annotation
@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = UniqueRollNumberValidator.class)
public @interface UniqueRollNumber {
    String message() default "Roll number already exists";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

// Validator — Spring injects the repository
@Component
public class UniqueRollNumberValidator
        implements ConstraintValidator<UniqueRollNumber, String> {

    private final StudentRepository studentRepository;

    public UniqueRollNumberValidator(StudentRepository studentRepository) {
        this.studentRepository = studentRepository;
    }

    @Override
    public boolean isValid(String rollNumber, ConstraintValidatorContext ctx) {
        if (rollNumber == null || rollNumber.isBlank()) return true; // @NotBlank handles this

        boolean exists = studentRepository.existsByRollNumber(rollNumber);
        if (exists) {
            ctx.disableDefaultConstraintViolation();
            ctx.buildConstraintViolationWithTemplate(
                "Roll number '%s' is already taken".formatted(rollNumber))
                .addConstraintViolation();
        }
        return !exists;
    }
}

// Usage on the request record
public record CreateStudentRequest(
    @NotBlank
    @Pattern(regexp = "^S\\d{3}$")
    @UniqueRollNumber   // DB check
    String rollNumber,

    @NotBlank @Size(min = 2, max = 100) String name,
    @NotBlank @Email String email
) {}
Validation Groups
OnCreate group applies @UniqueRollNumber — roll number must be unique when creating. OnUpdate group skips it — an update doesn't need to check its own existing roll number.
1 High Level Overview

Validation groups let you activate different constraints depending on the operation. Define marker interfaces (OnCreate, OnUpdate). Annotate constraints with groups = OnCreate.class. Use @Validated(OnCreate.class) on the controller method to activate only that group's constraints.

3 In This Project
validation/ValidationGroups.java · controller/AdminController.java
// 1. Define group marker interfaces
public interface ValidationGroups {
    interface OnCreate {}
    interface OnUpdate {}
}

// 2. Apply groups to constraints on the record
public record StudentRequest(

    @NotBlank(groups = {OnCreate.class, OnUpdate.class})
    @UniqueRollNumber(groups = OnCreate.class)   // only checked on create
    String rollNumber,

    @NotBlank(groups = {OnCreate.class, OnUpdate.class})
    @Size(min = 2, max = 100, groups = {OnCreate.class, OnUpdate.class})
    String name,

    @NotBlank(groups = {OnCreate.class, OnUpdate.class})
    @Email(groups = {OnCreate.class, OnUpdate.class})
    String email
) {}

// 3. Activate the right group on the controller
@PostMapping("/students")
@ResponseStatus(HttpStatus.CREATED)
public StudentDTO create(
        @Validated(OnCreate.class) @RequestBody StudentRequest request) {
    // @UniqueRollNumber fires here — creates are checked for uniqueness
    return studentService.createStudent(request);
}

@PutMapping("/students/{id}")
public StudentDTO update(
        @PathVariable Long id,
        @Validated(OnUpdate.class) @RequestBody StudentRequest request) {
    // @UniqueRollNumber does NOT fire here — updating doesn't need uniqueness check
    return studentService.updateStudent(id, request);
}
Validation Error Response
GlobalExceptionHandler catches MethodArgumentNotValidException and returns a 400 ProblemDetail with a map of field → error message so the frontend can highlight the exact invalid fields.
3 In This Project
exception/GlobalExceptionHandler.java
@ExceptionHandler(MethodArgumentNotValidException.class)
public ProblemDetail handleValidation(MethodArgumentNotValidException ex,
                                       HttpServletRequest request) {
    var problem = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
    problem.setTitle("Validation Failed");
    problem.setInstance(URI.create(request.getRequestURI()));

    // Collect all field errors into a map
    Map<String, String> fieldErrors = new LinkedHashMap<>();
    ex.getBindingResult().getFieldErrors()
        .forEach(e -> fieldErrors.put(e.getField(), e.getDefaultMessage()));

    // Collect global errors (class-level constraints)
    List<String> globalErrors = ex.getBindingResult().getGlobalErrors()
        .stream().map(DefaultMessageSourceResolvable::getDefaultMessage).toList();

    problem.setProperty("errors", fieldErrors);
    if (!globalErrors.isEmpty()) {
        problem.setProperty("globalErrors", globalErrors);
    }
    return problem;
}
