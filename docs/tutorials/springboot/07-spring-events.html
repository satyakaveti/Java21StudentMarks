Spring Events

Spring's event system decouples publishers from subscribers. When marks are updated, ResultService publishes a MarksUpdatedEvent — it doesn't know or care who listens. NotificationService sends an email. AuditService writes a log. Both fire independently without ResultService calling them directly.

Why Events?
Without events, ResultService would directly call NotificationService, AuditService, and CacheService — tightly coupling unrelated concerns. Events decouple them.
1 High Level Overview

Compare these two approaches:

Without events — tight couplingSimple
// ❌ ResultService knows about 4 other services
public MarkDTO createMark(Long studentId, CreateMarkRequest req) {
    var mark = save(req);
    notificationService.sendEmail(studentId);  // coupled!
    auditService.logCreate(mark);               // coupled!
    cacheService.evict(studentId);              // coupled!
    sseService.pushToStudent(studentId);        // coupled!
    return toDTO(mark);
}

// ✅ With events — ResultService publishes one event, knows nothing else
public MarkDTO createMark(Long studentId, CreateMarkRequest req) {
    var mark = save(req);
    publisher.publishEvent(new MarksUpdatedEvent(studentId, mark.getId()));
    return toDTO(mark);
    // Email, audit, cache eviction, SSE — all happen in listeners
}
Custom Events
MarksUpdatedEvent, StudentCreatedEvent, StudentDeletedEvent — plain Java records (Java 16) carrying the data listeners need.
1 High Level Overview

Events can be any Java object — they don't need to extend ApplicationEvent (that was required pre-Spring 4.2, now optional). Using Java records makes them immutable and concise. Include only the data listeners need — typically IDs, not full entities.

ApplicationEventPublisher
Injected into StudentService and ResultService — publishEvent() fires the event synchronously by default (all listeners run in the same thread before the method returns).
1 High Level Overview

ApplicationEventPublisher is the interface to publish events. Spring Boot's ApplicationContext implements it. Inject it via constructor. publishEvent(Object) delivers the event to all matching @EventListener methods immediately (synchronously, same thread) unless the listener is @Async.

3 In This Project
service/ResultService.java
@Service
public class ResultService {

    private final MarkRepository markRepository;
    private final ApplicationEventPublisher eventPublisher;  // inject publisher

    public ResultService(MarkRepository markRepository,
                         ApplicationEventPublisher eventPublisher) {
        this.markRepository = markRepository;
        this.eventPublisher = eventPublisher;
    }

    @Transactional
    @Auditable(action = "CREATE_MARK")
    public MarkDTO createMark(Long studentId, CreateMarkRequest request) {
        var mark = new Mark(studentId, request.subjectId(), request.score());
        var saved = markRepository.save(mark);

        // Publish — ResultService doesn't know who handles this
        eventPublisher.publishEvent(new MarksUpdatedEvent(
            studentId, saved.getId(),
            request.subjectName(), request.score()));

        return toDTO(saved);
    }
}
@EventListener
Synchronous audit log listener — runs in the same transaction as the publisher. Guaranteed to write the audit entry before the HTTP response returns.
1 High Level Overview

@EventListener marks a method as an event handler. Spring matches events by the method parameter type. A method can handle multiple event types by listing them in the annotation. Synchronous by default — runs in the same thread and transaction as the publisher.

2 Examples
Basic event listenerSimple
@Component
public class AuditEventListener {

    private final AuditLogRepository auditLogRepository;

    public AuditEventListener(AuditLogRepository auditLogRepository) {
        this.auditLogRepository = auditLogRepository;
    }

    // Spring calls this when any MarksUpdatedEvent is published
    @EventListener
    public void onMarksUpdated(MarksUpdatedEvent event) {
        auditLogRepository.save(AuditLog.builder()
            .action("MARKS_UPDATED")
            .entityId(event.studentId())
            .details("Mark %d updated to %d in %s"
                .formatted(event.markId(), event.newScore(), event.subjectName()))
            .build());
    }

    // Handle multiple event types
    @EventListener
    public void onStudentLifecycle(StudentCreatedEvent event) {
        auditLogRepository.save(AuditLog.of("STUDENT_CREATED", event.studentId()));
    }
}
Conditional listenerMedium
// Only fires if the score is a fail (below 35)
@EventListener(condition = "#event.newScore < 35")
public void onStudentFailed(MarksUpdatedEvent event) {
    log.warn("Student {} failed {} with score {}",
        event.studentId(), event.subjectName(), event.newScore());
    // Send alert to teacher
}
@TransactionalEventListener
Email notification uses AFTER_COMMIT phase — email is sent only after the DB transaction successfully commits. If the DB write fails, no email is sent.
1 High Level Overview

@TransactionalEventListener hooks into the transaction lifecycle. AFTER_COMMIT (most common) fires after the transaction commits — guarantees the data is in the DB before side effects run. AFTER_ROLLBACK fires on rollback. BEFORE_COMMIT fires before commit. Critical for: never sending emails for data that got rolled back.

2 Examples
AFTER_COMMIT vs @EventListenerMedium
// ❌ @EventListener — fires even if the transaction rolls back
// Student might get an email for data that was never saved!
@EventListener
public void sendEmail(MarksUpdatedEvent event) {
    emailService.send(event.studentId(), "Your marks are ready");
}

// ✅ @TransactionalEventListener — fires ONLY after DB commit
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void sendEmail(MarksUpdatedEvent event) {
    emailService.send(event.studentId(), "Your marks are ready");
    // Guaranteed: marks are in DB before this email goes out
}

service/NotificationService.java
@Service
public class NotificationService {

    private final EmailClient emailClient;
    private final StudentRepository studentRepository;

    public NotificationService(EmailClient emailClient,
                                StudentRepository studentRepository) {
        this.emailClient = emailClient;
        this.studentRepository = studentRepository;
    }

    // Fires ONLY after the DB transaction commits — safe to send email
    @Async
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void onMarksUpdated(MarksUpdatedEvent event) {
        var student = studentRepository.findById(event.studentId()).orElse(null);
        if (student == null) return;

        emailClient.send(
            student.getEmail(),
            "Your %s results are ready".formatted(event.subjectName()),
            "Hi %s, your score: %d".formatted(student.getName(), event.newScore())
        );
    }

    @Async
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void onStudentCreated(StudentCreatedEvent event) {
        emailClient.send(
            event.email(),
            "Welcome to Student Portal",
            "Hi %s, your roll number is %s".formatted(event.name(), event.rollNumber())
        );
    }
}
@Async on Event Listeners
All notification listeners are @Async — email sending runs on a virtual thread, not blocking the HTTP request thread that triggered the mark update.
1 High Level Overview

@Async on a listener makes it run on a separate thread (the virtualThreadExecutor in this project). This is critical for slow I/O like email sending — you don't want a 200ms SMTP call blocking the admin's "update mark" HTTP response. Spring submits the listener to the executor and returns to the caller immediately.

3 In This Project
service/NotificationService.java + config/AsyncConfig.java
// Listener — @Async + @TransactionalEventListener combined
@Async("virtualThreadExecutor")   // named executor from AsyncConfig
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onMarksUpdated(MarksUpdatedEvent event) {
    // Runs on a Java 21 virtual thread — non-blocking for the caller
    emailClient.send(...);  // slow SMTP call is fine here
}

// 1. Admin PUT /api/admin/marks/1  { score: 88 }
// 2. ResultService.updateMark() saves to DB
// 3. Transaction commits
// 4. Spring submits email task to virtual thread pool (non-blocking)
// 5. Admin receives HTTP 200 response immediately  ← fast!
// 6. Email is sent on background virtual thread    ← async!
